# Idempotency Key

An **idempotency key** is a unique identifier generated by the client and attached to a request. It allows the server to detect and safely ignore duplicate requests, returning the cached result of the original without re-executing the operation.

## Why It's Needed

Networks are unreliable. A client may retry a request after a timeout without knowing if the original succeeded. Without idempotency keys, retries can cause:

- **Duplicate charges** in payment systems
- **Double-created orders** in e-commerce
- **Multiple emails** sent to users

## How It Works

```
1. Client generates: idempotency_key = UUID()
2. Client sends: POST /payments { amount: 100, idempotency_key: "k-abc123" }
3. Server:
   - Check deduplication store for "k-abc123"
   - Not found → process payment, store result under "k-abc123", return 200
4. Network failure; client retries:
   - POST /payments { amount: 100, idempotency_key: "k-abc123" }
5. Server:
   - Found "k-abc123" → return cached 200 result (no duplicate charge)
```

## Implementation Details

| Concern | Recommendation |
|---------|---------------|
| **Key generation** | Client-side UUID v4 (random, no coordination needed) |
| **Storage** | Redis (fast lookups, TTL support) or DB table with unique constraint |
| **TTL** | Match the client's retry window (e.g., 24 hours) |
| **Concurrency** | Atomic "insert if not exists" to prevent race conditions on simultaneous retries |
| **HTTP header** | `Idempotency-Key: k-abc123` (Stripe convention) |

## Real-World Examples

- **Stripe** — requires `Idempotency-Key` header on all POST requests
- **PayPal** — uses `PayPal-Request-Id` header
- **AWS** — uses `ClientToken` for EC2, SQS, and other operations

## Relationship to HTTP Idempotency

HTTP GET, PUT, DELETE are inherently idempotent (by design). POST is not — idempotency keys are the standard mechanism to make POST operations idempotent when needed.
